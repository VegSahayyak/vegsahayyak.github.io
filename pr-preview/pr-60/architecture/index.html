Native Security & Hardening (Native Engine) ​

In v2.2.2, core telematics signal processing and license validation routines are compiled directly into the SDK's Native C++ Engine. This provides defense-in-depth protection for commercial enterprise integrations:

  • Runtime Integrity Checks: The native engine inspects /proc/self/maps at runtime to detect dynamic hooking frameworks (such as Frida or Xposed) and memory tampering.
  • Time-Travel & GPS Spoofing Defense: Implements high-water mark timestamp validation to reject manipulated, replayed, or reversed GPS fix packets.
  • Compiled Signal Processing: Velocity smoothing (EMA) and dynamic boundary math are computed directly in native C++ with hidden symbol visibility (-fvisibility=hidden), cryptographically coupled to active license memory state.
  • Minimal Binary Footprint: Fully stripped to less than 300KB per ABI (arm64-v8a, armeabi-v7a, x86, x86_64), preserving the SDK's lightweight footprint with zero impact on host application APK size.

Two-Tier Enterprise Licensing & Privacy-First Telemetry ​

The SDK operates on a dual-tier, offline-first Commercial Enterprise License and Privacy-First Telemetry model, eliminating runtime third-party authentication servers or tracking dependencies:

1. Two-Tier Licensing Model ​

  1. Tier 1 (Application Layer / Cryptographic Claims): On-device offline RSA-2048 JWT verification in Kotlin (LicenseManager) parses signed tokens encoding authorized module entitlements (such as :speed-ui, :speed-overlay, :speed-autostart) and expiration bounds.
  2. Tier 2 (Native Hardening & Math Coupling): All velocity calculations and boundary logic inside the native engine are cryptographically coupled to the valid license key. Fleets and logistics vehicles operate uninterrupted in remote, tunnel, or off-grid environments without periodic server ping requirements.

2. Privacy-First Telemetry Policy ​

Privacy-First Telemetry Guarantee

Core speed tracking operates 100% offline. For tiered commercial licenses, a lightweight periodic heartbeat transmits session duration and total distance traveled for billing reconciliation. Zero GPS coordinates, routes, or location points are ever logged, cached, or transmitted to any remote server or third-party cloud.

  • 100% On-Device Velocity Processing: All speed calculations, smoothing, and boundary alarms occur locally in memory.
  • Aggregated Heartbeat for Tiered Licenses: For commercial tiered licenses, a lightweight periodic heartbeat (TelemetryJobService) reports only aggregate session metrics: session duration (duration_ms), cumulative distance traveled (distance_meters), and client ID for billing reconciliation.
  • Zero Location Data Transmitted: Zero GPS coordinates, waypoints, routes, or location tracks are ever recorded, cached, or transmitted to any remote server or third-party cloud. Enterprises retain full data sovereignty and effortless compliance with global privacy regulations (GDPR, California CCPA, India DPDP).
  • Zero Overhead for Unlimited Tiers: Unlimited enterprise license holders bypass telemetry logging and synchronization completely.

Signal Processing & Telematics Engine ​

GPS hardware sensors on mobile devices frequently produce velocity noise spikes, multipath signal reflections, and intermittent signal drift (especially in urban canyons or under bridges). The TelematicsEngine in speed-core applies a multi-stage mathematical pipeline before emitting speed updates.

Live TelematicsEngine Mathematics Pipeline
EMA Factor (α): 0.30
SmoothedVelocity[t] = 0.30 · Raw[t] + 0.70 · Smoothed[t-1]Trigger: > Upper Limit | Dismiss: < Lower Hysteresis Bound
TimestampRaw GPS (Jitter)EMA SmoothedHysteresis State

1. Accuracy Confidence Gating ​

Raw GPS fixes with an estimated horizontal accuracy greater than our proprietary internal threshold (20.0 meters) or missing speed precision are discarded:

Gating Rule

text
Accept GPS Fix IF: horizontalAccuracy <= CONFIDENCE_THRESHOLD (2σ confidence)

When a reading is rejected, the engine emits SpeedData.LowAccuracy, preventing erratic spikes while preserving the last valid smoothed speed.

2. Native Exponential Moving Average (EMA) Smoothing ​

To eliminate abrupt needle shaking while retaining immediate responsiveness to actual vehicle acceleration, the engine applies an Exponential Moving Average executed directly within the native C++ engine:

Mathematical Smoothing Formula

text
SmoothedVelocity[t] = α · RawVelocity[t] + (1 - α) · SmoothedVelocity[t - 1]
  • S_t: Smoothed speed at timestamp t (in meters/second).
  • Y_t: Raw velocity reading from the GPS provider.
  • S_{t-1}: Previous smoothed speed state.
  • α: Proprietary calibrated smoothing coefficient, executed securely inside the native engine with immediate snap-to-speed on standstill or trip start.

3. Dynamic Speed Limit Thresholding & Safety Logic ​

Speed limits are automatically derived from the active DrivingProfile (e.g. CarHighway, SchoolZone, EScooter):

  • Over-Speed Alert: Triggers deterministically when smoothed speed exceeds the profile limit (smoothedSpeed > warningThresholdMps), immediately setting isOverLimit = true.
  • Under-Speed Corridor Warning: When a minimum speed corridor is configured, triggers when driving speed drops below the corridor floor (isUnderLimit = true).
  • Stationary Suppression: To avoid annoying false under-speed warnings when starting a vehicle, waiting at traffic lights, or navigating speed bumps, under-speed alerts are automatically silenced during stop-and-go conditions.
  • Clean Deterministic Boundaries: Pre-filtering raw sensor noise via native EMA smoothing removes the need for artificial hysteresis dismissal lags (which can cause alarms to hang after a driver has decelerated and unfairly penalize driver safety scores).

  1. AutoStartManager (:speed-autostart): This is the new recommended strategy for battery optimization.
